# Computer Networks I: Java serial communications programming

This is the assignment text issued by the course staff (Department of Electrical and Computer Engineering, Aristotle University of Thessaloniki), "Computer Networks I", experimental virtual lab. It is a shortened English translation of the Greek handout: the parts about installing Java, serial-port programming on Windows and the submission rules are left out, and so are the questions the handout puts to the student. Only the translation is new.

## Purpose

The assignment is a network programming exercise. It aims (a) to develop an experimental network application in Java, (b) to get hands-on experience with asynchronous serial communication between computers and (c) to collect statistical measurements of parameters that, among others, determine the quality of communication over real physical channels. Some measurements have to be made against the Ithaki server of the experimental virtual lab that the courses Computer Networks I and II share.

## The virtual modem

The server provides the class `Modem`, which lets a program communicate serially with a local virtual modem and through it with the Ithaki server over an ordinary Internet connection. A modem is created with `Modem modem = new Modem(speed)`, where `speed` is the requested speed from 1 kbps to 80 kbps. For requested speeds below 8 kbps the actual speed is the nearest integer multiple of 1 kbps, and up to 80 kbps the nearest integer multiple of 8 kbps. The speed is constant after `modem.fixed(true)`; otherwise it varies at random times, below the requested speed, to imitate a real telephone channel.

The object reads and writes bytes with `modem.read()` and `modem.write(int x)` or `modem.write(byte[] x)`. `read()` blocks until at least one byte is available, the end of the stream is detected or an exception such as a timeout occurs. The other end of the streams is always connected to a similar remote virtual modem on the Ithaki server. `read()` returns -1, and `write()` returns `false`, when the streams are not available, for example when the connection to the server is lost. The methods `modem.speed(int speed)`, `modem.setTimeout(int timeout)`, `modem.open(String destination)`, `modem.close()`, `modem.getInputStream()` and `modem.getOutputStream()` set the speed, set the idle time after which the call is dropped, activate and deactivate the modem, and create the input and output streams.

The command `java Modem` opens a virtual terminal for trying the connection. The modem answers a limited set of AT commands: `AT`, `ATI`, `ATS`, `ATS=<speed>`, `ATH1`, `ATH0`, and `ATD2310ITHAKI` to call the lab server. After `java Modem` the modem is in command mode and answers only AT commands; once `ATD2310ITHAKI` has connected it to the remote modem it is in data mode, and every character or byte sent to it is passed on to the Ithaki server unchanged. `+++ATH0` followed by a carriage return hangs up: `+++` is the escape sequence that returns the modem from data mode to command mode.

## The application

The task is a Java application, `userApplication`, that (a) talks to the lab server through one of the eight virtual modems that answer to the call number 2310-ITHAKI and (b) measures some parameters of that communication. The features and the measurements follow.

1. When the student chooses the assignment "Java serial communications programming" on the lab's web page, the server accepts them for a two-hour session and gives the parameters needed for the application.
2. Up to 60 seconds pass between choosing the assignment and the activation of the parameters. After the two hours, a new choice of the same assignment gives new parameter values.
3. **Echo packets.** The application must be able to receive many `echoPacket`s one after the other, each time after sending the code `echo_request_code` to the server. The code has the form `EXXXX` and is given at the start of the session. Echo packets have the form `PSTART DD-MM-YYYY HH-MM-SS PC PSTOP`, where `PC` is a packet counter modulo 100.
4. **Images.** Sending `image_request_code`, of the form `MXXXX`, returns the current frame of the lab's video coder, which shows the traffic in front of the School of Engineering. The transfer is 8 to 80 kilobytes depending on lighting, activity in the field of view and the requested frame size. Saved as a binary file with the extension `.jpeg` or `.jpg`, it can be shown in any image viewer. A JPEG file starts with the bytes `0xFF 0xD8` and ends with `0xFF 0xD9`. The code can be followed by `CAM=FIX` or `CAM=PTZ`, which selects the camera: the fixed one (the default) gives 640x480 pixels at a fixed angle, the second gives 320x240 pixels and an angle that changes at random times while the camera is under pan-tilt-zoom control. `CAM=PTZ` can be followed by `DIR=X`, where `X` is `L` (left), `U` (up), `R` (right) or `D` (down) to move the camera, `M` to memorise the current angle or `C` to return to the memorised one. The camera takes a few seconds to react. With the broadband virtual modem `CAM=XX` selects a camera of the Thessaloniki ring road telematics system, optionally followed by `SIZE=L` or `SIZE=S`. Each frame carries the moving average of the frame rate and of the transmission speed. For safety the modem connection has a timeout, so a large JPEG at a low speed can be cut short.
5. **GPS.** Sending `gps_request_code`, of the form `PXXXX`, returns a stream of GPS fixes in the NMEA serial protocol. Each sentence begins with a header that identifies it and ends with `<CR><LF>`. An example: `$GPGGA,045208.000,4037.6331,N,02257.5633,E,1,07,1.5,57.8,M,36.1,M,,0000*6D`, where `$GPGGA` is the header, 04:52:08 the time, 40 degrees 37.6331 minutes north and 22 degrees 57.5633 minutes east the position, 07 the number of satellites and 57.8 m the height above sea level. The fixes come from stored routes in Thessaloniki or, if the server is receiving a live route, from anywhere. With the parameter `R=XPPPPLL` after the code, the server sends `LL` fixes of the stored route `X`, starting with fix `PPPP`. The server adds `START ITHAKI GPS TRACKING\r\n` at the start of the stream and `STOP ITHAKI GPS TRACKING\r\n` at its end. The parameter `T=AABBCCDDEEZZ`, which can be repeated up to nine times after the code, asks for a position with longitude AA degrees BB minutes CC seconds and latitude DD degrees EE minutes ZZ seconds to be marked on a JPEG map image from Google Maps that the server returns.
6. **Transmission errors.** The server causes pseudo-random errors before packets enter the channel, in two cases.
   - An image request code of the form `GXXXX` introduces errors while the current frame is sent. They fall in the second half of the image so that they are visible in the JPEG.
   - Errors in single packets are handled with an ARQ (automatic repeat request) mechanism. The codes `QXXXX` and `RXXXX` are used. The first is sent as a positive acknowledgement (ACK) and at the same time as a request for the next new packet; the second is a negative acknowledgement (NACK) and a request to repeat the same packet. The packets have the form `PSTART DD-MM-YYYY HH-MM-SS PC <XXXXXXXXXXXXXXXX> FCS PSTOP`, where `<XXXXXXXXXXXXXXXX>` is a 16-character encrypted sequence taken from a pseudo-random position in a text, and the server introduces errors at pseudo-random positions in it. `FCS` (frame check sequence) is a 3-digit decimal number, the result of applying XOR to the 16 characters in turn. On receiving a packet the application checks the sequence against `FCS` and answers with ACK or NACK.

In applications that use the virtual modem, request codes must be followed by the character `\r` (ASCII 13) as a delimiter.

## Measurements and presentation of results

- **A.** Results from at least two sessions at least 48 hours apart.
- **B.** From each session: (i) a graph G1 of the response time, in milliseconds, of every packet sent over at least 4 minutes; (ii) two images E1 and E2 from the lab's video coder, one without and one with transmission errors; (iii) an image M1 with at least four GPS fixes, each at least four seconds after the previous one, taken from sentences of route X=1 of your choice; (iv) a graph G2 of the response time, in milliseconds, of every packet received successfully with the ARQ mechanism under pseudo-random errors, over at least 4 minutes.
- **C.** From the measurements of B (iv): (a) an estimate of the probability distribution of the number of retransmissions, presented as a graph G3 of a suitable type such as a bar chart, and (b) an estimate of the error probability in the experiments, given as the (simple) calculation of the bit error rate (BER).
- **D.** Short comments on the measurements and graphs, and a short bibliographic technical reference to the mechanisms and protocols of the modem devices used in similar applications.
